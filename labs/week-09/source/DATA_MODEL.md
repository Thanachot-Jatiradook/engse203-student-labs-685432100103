# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

---

## 1. ภาพรวม

ระบบ Campus Service Request มีโครงสร้างฐานข้อมูลเชิงสัมพันธ์ (Relational Database) ประกอบด้วย 2 ตารางหลัก ได้แก่ `users` และ `requests`

```
┌─────────────────────────────────┐           ┌─────────────────────────────────┐
│              users              │           │            requests             │
├─────────────────────────────────┤           ├─────────────────────────────────┤
│ PK  id          INTEGER (AUTO)  │ 1       N │ PK  id            TEXT          │
│     name        TEXT            ├───────────┤ FK  requester_id  INTEGER       │
│     department  TEXT            │           │     request_type  TEXT          │
│     email       TEXT UNIQUE     │           │     location      TEXT          │
└─────────────────────────────────┘           │     details       TEXT          │
                                              │     priority      TEXT          │
                                              │     status        TEXT          │
                                              │     created_at    TEXT          │
                                              └─────────────────────────────────┘
```

**ความสัมพันธ์:** เป็นความสัมพันธ์แบบ **หนึ่งต่อหลาย (One-to-Many / 1:N)**
- ผู้ใช้งาน 1 คน (`users`) สามารถสร้างคำร้อง (`requests`) ได้หลายรายการ
- แต่ละคำร้อง (`requests`) จะต้องมีผู้แจ้งเพียง 1 คนเสมอ โดยเชื่อมโยงผ่าน Foreign Key `requester_id` ที่ชี้ไปยัง `users.id`

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ใน Week 06–07 มีการเก็บข้อมูลคำร้องในไฟล์ JSON เพียงไฟล์เดียว โดยเก็บ `requesterName` เป็นข้อความฝังอยู่ในทุกคำร้อง การทำแบบนี้ก่อให้เกิดปัญหาด้าน Data Redundancy และ Data Anomaly หลายประการ:

1. **ปัญหาการแก้ไขข้อมูล (Update Anomaly):**
   - **"ถ้าสมชายเปลี่ยนชื่อ ต้องแก้กี่ที่?"**
   - ในระบบเดิม หากสมชายส่งคำร้องไว้ 50 ใบ และต้องการเปลี่ยนชื่อ-นามสกุล หรือแก้ไขการสะกดชื่อ เราจะต้องไล่แก้ไขข้อมูลทั้ง 50 รายการ หากแก้ไม่ครบจะเกิดปัญหาข้อมูลไม่สอดคล้องกัน (Inconsistency)
   - แต่เมื่อแยกตาราง `users` ออกมา เราแก้ไขชื่อของสมชายเพียง **1 ที่** ในตาราง `users` ที่แถวของสมชายเท่านั้น คำร้องทุกใบที่เชื่อมผ่าน `requester_id` จะแสดงชื่อใหม่ทันทีเมื่อทำ `JOIN`
2. **ปัญหาข้อมูลสูญหาย (Deletion Anomaly):**
   - ในระบบเดิม หากลบคำร้องทั้งหมดของนายสมชาย ข้อมูลของนายสมชาย เช่น แผนกและอีเมล ก็จะสูญหายไปจากระบบด้วย
   - เมื่อแยกตาราง แม้จะลบคำร้องทั้งหมด ข้อมูลโปรไฟล์ผู้ใช้งานในตาราง `users` ก็ยังคงอยู่
3. **ปัญหาการบันทึกข้อมูลซ้ำซ้อน (Data Redundancy):**
   - การเก็บชื่อ, แผนก, อีเมล ซ้ำๆ ทุกคำร้อง สิ้นเปลืองเนื้อที่จัดเก็บ และเสี่ยงต่อการพิมพ์ชื่อผิดหรือสะกดไม่เหมือนกัน เช่น "สมชาย ใจดี" กับ "สมชาย  ใจดี" (มีเว้นวรรค 2 เคาะ)
4. **การรับประกันความถูกต้อง (Referential Integrity):**
   - การใช้ Foreign Key ร่วมกับ `PRAGMA foreign_keys = ON;` ป้องกันไม่ให้มีการสร้างคำร้องโดยอ้างอิง `requester_id` ที่ไม่มีอยู่จริงในระบบ

## 3. รายละเอียดตาราง

### ตาราง `users`

| คอลัมน์ | ชนิด | ข้อกำหนด (Constraints) | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| `id` | `INTEGER` | `PRIMARY KEY AUTOINCREMENT` | ใช้ตัวเลขจำนวนเต็มเรียงลำดับอัตโนมัติ สะดวกในการอ้างอิง Foreign Key และค้นหาได้รวดเร็ว |
| `name` | `TEXT` | `NOT NULL` | ชื่อผู้ใช้จำเป็นต้องมีเสมอ ห้ามเป็นค่าว่าง |
| `department` | `TEXT` | `NOT NULL` | ใช้ระบุสังกัด/ภาควิชาของผู้ใช้เพื่อการติดตามงาน |
| `email` | `TEXT` | `NOT NULL UNIQUE` | อีเมลของมหาวิทยาลัยใช้ระบุตัวตนและห้ามซ้ำกันในระบบ |

### ตาราง `requests`

| คอลัมน์ | ชนิด | ข้อกำหนด (Constraints) | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| `id` | `TEXT` | `PRIMARY KEY` | ใช้รหัสที่มนุษย์เข้าใจง่ายและขึ้นต้นด้วย `REQ-` ตามข้อกำหนด API Contract เดิม เช่น `REQ-001` |
| `requester_id` | `INTEGER` | `NOT NULL, REFERENCES users(id)` | Foreign Key เชื่อมไปยังผู้ใช้ บังคับว่าต้องมีผู้แจ้งคำร้องจริงในตาราง `users` |
| `request_type` | `TEXT` | `NOT NULL, CHECK (request_type IN ('แจ้งซ่อม','บริการบัญชีผู้ใช้','ขอใช้อุปกรณ์','อื่น ๆ'))` | จำกัดประเภทให้ตรงตาม 4 หมวดหมู่ที่ระบบรองรับ ป้องกันข้อมูลผิดพลาด |
| `location` | `TEXT` | `NOT NULL` | สถานที่ต้องไม่เป็นค่าว่าง เพื่อให้เจ้าหน้าที่เข้าปฏิบัติงานได้ |
| `details` | `TEXT` | `NOT NULL` | รายละเอียดปัญหา/ความต้องการ ห้ามว่าง |
| `priority` | `TEXT` | `NOT NULL DEFAULT 'normal', CHECK (priority IN ('normal','urgent'))` | จำกัดความสำคัญ 2 ระดับ ค่าเริ่มต้นคือ `'normal'` |
| `status` | `TEXT` | `NOT NULL DEFAULT 'pending', CHECK (status IN ('pending','in-progress','completed'))` | จำกัดสถานะวงจรคำร้อง 3 สถานะ ค่าเริ่มต้นคือ `'pending'` |
| `created_at` | `TEXT` | `NOT NULL DEFAULT (datetime('now','localtime'))` | บันทึกวันเวลาที่สร้างคำร้องอัตโนมัติในรูปแบบ ISO-8601 string |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

1. **ทำไม `users.id` กับ `requests.id` ใช้ชนิดต่างกัน:**
   - `users.id` เป็น `INTEGER AUTOINCREMENT`: ทำหน้าที่เป็น surrogate key ภายในระบบ ไม่จำเป็นต้องสื่อความหมายต่อผู้ใช้ภายนอก การใช้ตัวเลขจำนวนเต็มช่วยให้การทำ Index และคำสั่ง `JOIN` ทำงานได้เร็วที่สุด
   - `requests.id` เป็น `TEXT` (เช่น `REQ-001`): เป็น business key ที่แสดงผลบน UI ให้ผู้ใช้งานจดจำและติดตามสถานะ การใช้ `TEXT` ช่วยรักษาความเข้ากันได้กับ API Contract และ Frontend ที่พัฒนาไว้ตั้งแต่ Week 06–07 โดยไม่ต้องแก้โค้ดฝั่งหน้าบ้าน
2. **ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว:**
   - ปฏิบัติตามหลักการ **Defense in Depth** (การป้องกันหลายชั้น)
   - หากในอนาคตมีช่องทางอื่นในการเพิ่มข้อมูลเข้ามา เช่น สคริปต์ Migration, Direct CLI, ฐานข้อมูล Admin, หรือ Background Job ที่ไม่ได้ผ่าน Validation Middleware ของ Express ตัว Database Engine ก็จะยังคงปฏิเสธข้อมูลที่ไม่ถูกต้องเสมอ ทำให้ข้อมูลคงความถูกต้องสมบูรณ์ (Data Integrity) ตลอดเวลา

## 5. ตัวอย่างการใช้ JOIN

คำสั่ง SQL ในการดึงข้อมูลคำร้องพร้อมแสดงชื่อผู้แจ้ง:

```sql
SELECT r.id,
       u.name AS requesterName,
       r.request_type,
       r.location,
       r.details,
       r.priority,
       r.status
FROM requests r
JOIN users u ON u.id = r.requester_id
ORDER BY r.id ASC;
```

**ผลลัพธ์ที่ได้:**

| id | requesterName | request_type | location | details | priority | status |
|---|---|---|---|---|---|---|
| REQ-001 | สมชาย ใจดี | แจ้งซ่อม | ห้องปฏิบัติการ 301 | เครื่องปรับอากาศไม่ทำงานตั้งแต่เช้า | urgent | pending |
| REQ-002 | สุภาวดี รักเรียน | บริการบัญชีผู้ใช้ | อาคารวิศวกรรม | เข้าสู่ระบบห้องปฏิบัติการไม่ได้ | normal | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ | ขอใช้อุปกรณ์ | ห้องประชุม 2 | ขอยืมโปรเจกเตอร์สำหรับนำเสนอโครงงาน | normal | completed |
| REQ-004 | สมชาย ใจดี | แจ้งซ่อม | ห้องปฏิบัติการ 302 | คอมพิวเตอร์เครื่องที่ 5 เปิดไม่ติด | urgent | pending |
| REQ-005 | ปรียา ขยันยิ่ง | อื่น ๆ | ห้องสมุด ชั้น 2 | ขอเพิ่มปลั๊กไฟบริเวณโต๊ะอ่านหนังสือ | normal | pending |

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

- ผลลัพธ์จากการทำ `JOIN` ร่วมกับการใช้ alias `u.name AS requesterName` ได้โครงสร้าง object และ field names ที่เหมือนกับข้อมูลที่ API ส่งให้ React ในสัปดาห์ที่ 7 ทุกประการ
- สิ่งนี้ทำให้ในสัปดาห์ที่ 10 เมื่อเปลี่ยน `requestService.js` จากการอ่าน JSON ไปคิวรีฐานข้อมูล SQLite เราสามารถใช้คำสั่ง SQL นี้แทนที่ได้ทันทีโดยไม่ต้องแก้ไข Controller หรือโค้ดฝั่ง Frontend React เลยแม้แต่บรรทัดเดียว
